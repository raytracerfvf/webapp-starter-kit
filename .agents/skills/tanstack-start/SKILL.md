# TanStack Start

## Execution boundaries

- Route loaders are isomorphic — they run on server *and* client. Privileged work goes through server
  functions or `.server.ts` modules.
- The router plugin splits render-only options (`component`, `errorComponent`, `pendingComponent`,
  `notFoundComponent`); the root route is not split. `validateSearch`, `loader`, `beforeLoad`, `head`, and
  their static imports stay eager and ship in the entry bundle.
- Eager options import only lightweight `lib/**` schemas, constants, and query options — never components,
  contexts, heavy feature modules, or `@/server/**`. **Not machine-enforced**: an import used only by a split
  render option is legitimate, so trace which option reaches each import rather than rejecting every component
  import in a route file.
- Search-param schemas live in `lib/constants/`, paired with `loaderDeps` so loaders rerun only for the params
  they use.
- Auth route groups provide UX redirects; authorization stays in server functions and operations.
- A route whose content comes exclusively from a browser-only API may set `ssr: false`. The server then renders
  the route's `pendingComponent`, so browser state initializes synchronously without a hydration mismatch.
  Reach for this only when the data has no server representation.

## Root context

`routes/__root.tsx` assembles stable infrastructure: QueryClient and SSR integration, parsed optional
session/user context, router-level loader dependencies, error/not-found/pending boundaries, and dev-only
devtools. Do not add a second QueryClientProvider — the SSR integration already provides one. Routes consume
context rather than re-fetching.

## Query integration

The loader calls `await context.queryClient.ensureQueryData(options)` and returns nothing unless it has
distinct non-query data; the component calls the domain hook from `lib/hooks/use-<domain>-queries.ts`, which
consumes the same options with `useSuspenseQuery`. This avoids waterfalls and keeps complex loader return types
from inflating route-tree inference. Define `queryOptions` in `lib/queries/`, never in a route file.

## Loading states

- The router waits 200ms before showing a pending route and keeps a shown fallback visible for at least 500ms.
  The header shows a decorative progress line after 75ms so short waits have feedback without flashing the
  route fallback; the route pending state owns the accessible status message.
- Use a route `pendingComponent` with a layout-shaped skeleton when the destination geometry is known. Keep it
  side-effect-free and independent of feature hooks, contexts, and server modules. On an `ssr: false` route the
  server renders it as the fallback.
- Render-only options are split, but the router may group a route's UI options into one chunk — verify build
  output rather than assuming a separate source file produced a separate chunk.
- Use the configured default pending component for routes without a useful skeleton. Do not add manual Suspense
  boundaries around route components; the router owns the route boundary.
- Background refetches keep stale data visible. Suspense fallbacks represent missing route-critical data, not
  every `isFetching` transition.

## Server-only modules

- Sensitive files end in `.server.ts` and import `@tanstack/react-start/server-only` *(enforced at build time
  via `importProtection` in vite.config.ts)*.
- Database URLs, auth secrets, email keys, server logs, filesystem access, and privileged SDKs never enter
  client modules. Client-visible variables are deliberately `VITE_`-prefixed and separately validated.
- `routeTree.gen.ts` is generated by the router plugin during dev and build *(enforced: write-guard hook)*.

## Start instance and CSRF

Defining `src/start.ts` replaces Start's implicit middleware defaults, so CSRF must be installed explicitly:
`createCsrfMiddleware({ filter: (ctx) => ctx.handlerType === "serverFn" })`. Requests without same-origin
evidence stay rejected unless the deployment documents an equivalent control.

Registration order and placement:

- request context and correlation, before anything that uses them;
- CSRF for server functions;
- request logging and response/security headers, globally;
- error guarding and sanitization as *function* middleware — server-function errors are serialized before
  ordinary request error middleware can observe them.

## Required tests

- Search parsing, defaults, and `loaderDeps` behavior.
- Protected server calls reject direct unauthorized POSTs regardless of route navigation.
- Server-only imports fail client-boundary checks.
- SSR query hydration has no duplicate fetch, duplicate provider, or hydration mismatch.
- Pending timing and cleanup, side-effect-free layout skeletons, one accessible loading status.
- CSRF accepts valid same-origin calls and rejects cross-origin and missing-origin requests per policy.
